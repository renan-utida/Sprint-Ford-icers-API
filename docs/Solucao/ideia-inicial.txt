SpecRadar — Solução Completa Ford FIAP 2026
Visão Geral do Produto
O SpecRadar é uma plataforma de inteligência competitiva automotiva que resolve um problema real e documentado pela própria Ford: coletar especificações técnicas de veículos concorrentes consome aproximadamente 1 hora por versão de forma manual, com alta probabilidade de imprecisão. A plataforma elimina esse gargalo permitindo que o analista consulte qualquer veículo concorrente em linguagem natural ou via formulário estruturado, recebendo em segundos uma ficha técnica padronizada, sempre no mesmo formato, independentemente da marca, modelo ou versão consultada.
O diferencial central da solução é a combinação de dois modos de interação — um assistente conversacional para consultas rápidas e exploratórias, e uma interface estruturada para consultas formais e exportação de dados — sobre uma mesma base técnica robusta com API REST, banco de dados histórico e autenticação segura. Ao longo do ano, a plataforma evolui para aceitar qualquer tipo de fonte de dados, incluindo PDFs de catálogos, imagens e prints de fichas técnicas, tornando-se capaz de extrair especificações de fontes que nenhuma automação tradicional consegue processar.
Ideia Central
O analista de Product Marketing da Ford precisa entender como os concorrentes se posicionam em termos de preço, motorização, equipamentos e pacotes. Hoje ele faz isso manualmente — navega em sites, assiste vídeos, liga para concessionárias, lê PDFs — e no final tem uma planilha preenchida à mão que pode conter erros e que fica desatualizada rapidamente.
O SpecRadar substitui esse processo por dois fluxos complementares. No primeiro, o analista abre o app mobile ou acessa a interface web, digita em linguagem natural algo como "Quais são as especificações de motor e suspensão da Toyota Hilux GR-Sport 2025?" e o sistema responde com a ficha padronizada extraída automaticamente, armazenada no banco e disponível para comparação futura. No segundo fluxo, o analista preenche um formulário estruturado com Marca, Modelo, Versão e a lista de atributos que deseja pesquisar — exatamente como a Ford especificou no material — e recebe o mesmo resultado em formato de tabela exportável.
Os dois fluxos alimentam o mesmo banco de dados, o que significa que cada consulta feita por qualquer analista enriquece o histórico coletivo da plataforma. Com o tempo, o sistema acumula um repositório comparativo de especificações que pode ser consultado sem precisar buscar novamente na fonte.
Arquitetura Macro
A arquitetura é organizada em quatro camadas independentes e bem definidas, o que atende diretamente ao critério de SOA da disciplina de Web Services.
A primeira camada é a de ingestão e interação, responsável por receber as consultas dos usuários. Ela contém dois pontos de entrada: a interface conversacional, onde o usuário digita em linguagem natural, e o formulário estruturado, onde o usuário preenche os campos obrigatórios. Ambos se comunicam com o backend via API REST. O app mobile em React Native com Expo é o cliente principal, mas a API é aberta o suficiente para ser consumida por qualquer outro cliente no futuro.
A segunda camada é a de processamento e extração, que é o coração técnico da solução. Ela contém o serviço de IA — um LLM com capacidade de busca na web, como o modelo Claude ou GPT-4o com web search habilitado — que recebe a consulta estruturada e retorna um JSON com os campos solicitados preenchidos ou marcados como "não disponível". O prompt enviado ao modelo é cuidadosamente construído para garantir que a saída sempre respeite o schema predefinido, independentemente do veículo consultado. Há também um serviço de cache nessa camada: antes de chamar o LLM, o sistema verifica se aquela combinação de marca/modelo/versão já foi consultada recentemente e, em caso positivo, retorna do banco sem custo adicional de API.
A terceira camada é a de armazenamento e histórico, composta por um banco de dados relacional (PostgreSQL) com duas responsabilidades principais. A primeira é armazenar as fichas técnicas extraídas com metadados de fonte, data e usuário que realizou a consulta. A segunda é registrar o histórico de alterações — se o preço de um veículo muda entre duas consultas, o sistema mantém ambos os registros com timestamp, permitindo análise de evolução temporal.
A quarta camada é a de apresentação e alertas, que inclui o app mobile com as telas de consulta, comparação e histórico, além de um sistema de notificações push que alerta o analista quando uma especificação de um veículo monitorado é atualizada.
A comunicação entre todas as camadas passa pela API REST central em Java com Spring Boot, que é o único ponto de entrada para o banco de dados. O serviço de IA é um microserviço separado, chamado pela API principal, o que permite substituí-lo ou atualizá-lo sem impactar o restante do sistema.
O que Cada Matéria Entrega
Arquitetura Orientada a Serviços e Web Services
Esta é a disciplina que mais se beneficia da clareza arquitetural do projeto, porque a separação em serviços independentes é estrutural, não forçada.
Os endpoints principais da API REST são organizados em três grupos. O grupo de consulta inclui POST /specs/query que recebe marca, modelo, versão e lista de atributos e retorna a ficha padronizada em JSON; GET /specs/{marca}/{modelo}/{versao} que retorna a ficha armazenada no banco sem chamar o LLM; e GET /specs/compare que recebe dois ou mais veículos e retorna um comparativo lado a lado com destaque nas diferenças. O grupo de histórico inclui GET /specs/history/{marca}/{modelo}/{versao} que retorna a evolução temporal das especificações com timestamps. O grupo de chat inclui POST /chat/message que recebe a mensagem do usuário em linguagem natural e retorna a resposta do assistente junto com a ficha estruturada quando aplicável.
A arquitetura SOA se manifesta na separação clara entre o serviço de chat (que interpreta a intenção do usuário), o serviço de extração (que chama o LLM), o serviço de persistência (que gerencia o banco) e o serviço de notificações (que gerencia os alertas). Cada um pode ser escalado, testado e mantido de forma independente.
A documentação completa das APIs é feita com Swagger/OpenAPI, incluindo exemplos de request e response para cada endpoint, descrição dos campos obrigatórios e opcionais, códigos de erro tratados e contratos de autenticação.
O controle de migrações do banco é feito com Flyway, garantindo que alterações no schema sejam versionadas e reproduzíveis em qualquer ambiente.
Mobile Development and IoT (atualizado)
O app mobile tem três perfis de usuário com experiências distintas, mas que compartilham a mesma base de código React Native com Expo.
O perfil de analista comum tem acesso às seguintes telas: tela de consulta conversacional com interface de chat, onde as mensagens do assistente incluem a ficha técnica renderizada em cards dentro da própria conversa; tela de consulta estruturada com formulário de Marca, Modelo, Versão e seleção de atributos desejados a partir de uma lista predefinida e editável; tela de resultado com a ficha padronizada em formato de cards organizados por categoria (motorização, transmissão, segurança, conforto, preço), com indicação visual clara quando um campo está marcado como não disponível; tela de comparação lado a lado entre dois ou mais veículos, com destaque em verde para o campo superior e vermelho para o inferior em atributos numéricos como potência, torque e preço; tela de histórico com evolução temporal de um veículo específico, mostrando como preço e especificações mudaram ao longo do tempo; e tela de monitoramento, onde o analista define quais veículos deseja monitorar e recebe notificações push quando uma atualização é detectada.
O perfil de analista senior tem acesso a tudo que o analista comum tem, com uma funcionalidade adicional: a tela de configuração do schema de atributos da organização, onde pode adicionar, remover ou reorganizar os atributos padrão que aparecem nas consultas estruturadas para todos os usuários da plataforma. Essa diferenciação reforça o RBAC na prática — a tela existe no app mas é bloqueada por autorização para o perfil comum.
O perfil de administrador acessa todas as funcionalidades anteriores e tem um ícone adicional de configurações na navegação principal que dá acesso ao painel administrativo. Dentro desse painel estão disponíveis: gerenciamento de usuários e permissões (criar, desativar e alterar o perfil de cada usuário da organização), visualização dos logs de auditoria com filtros por usuário, data e veículo consultado, e métricas de uso da plataforma como número de consultas por período, veículos mais consultados e taxa de cache hit versus chamadas ao LLM. Esse painel não altera a experiência de navegação principal do app — o administrador ainda usa as mesmas telas de consulta que os outros perfis, com a camada administrativa acessível separadamente.
A navegação é implementada com Expo Router, o gerenciamento de estado com Context API ou Zustand, e o consumo das APIs é feito de forma assíncrona com tratamento de estados de loading, erro e sucesso em todas as telas. O controle de acesso às telas restritas é feito no lado do cliente verificando o perfil armazenado no token JWT, com validação reforçada no lado da API para cada requisição.
Funcionalidades que contam como diferenciais na avaliação: notificações push para alertas de atualização, armazenamento local do histórico de consultas recentes com AsyncStorage, e modo offline que permite visualizar fichas já consultadas sem conexão.
Testing, Compliance and Quality Assurance
O pitch do projeto é particularmente forte para esta disciplina porque o problema é quantificável, a solução é verificável e o impacto de negócio é direto.
O pitch apresenta o problema com os dados do próprio material da Ford (1 hora por versão, processo manual, imprecisão) e propõe a solução com métricas claras de sucesso: tempo médio de consulta abaixo de 30 segundos, taxa de campos corretamente preenchidos acima de 90% validada contra o ground truth da Ranger Raptor, e disponibilidade da plataforma acima de 99%.
O benchmarking analisa soluções existentes como a Tabela FIPE (que só traz preço, sem specs técnicas), o portal Quatro Rodas (que tem specs mas sem padronização nem API), o iSeeCars (focado no mercado americano) e as próprias planilhas internas da Ford (o processo atual). O SpecRadar se diferencia de todos por combinar extração automatizada, formato padronizado, interface conversacional e histórico temporal em uma única plataforma.
O Business Canvas detalha os segmentos de cliente (analistas de Product Marketing, gerentes de produto, equipes de pricing), os canais (app mobile, API direta para integração com ferramentas internas), a proposta de valor (eliminar trabalho manual repetitivo e impreciso), as atividades-chave (manutenção do modelo de extração, curadoria do schema de dados), os recursos necessários (créditos de API de LLM, infraestrutura de banco de dados), os parceiros (Anthropic ou OpenAI para o modelo de IA, provedor de cloud), os custos (API de LLM por token, infraestrutura) e as fontes de receita ou redução de custo (horas economizadas multiplicadas pelo custo hora do analista).
A arquitetura TOGAF no Archi apresenta as quatro perspectivas: visão estratégica (eliminar o processo manual de coleta de specs), arquitetura de negócio (como o fluxo de trabalho do analista muda com a solução), arquitetura de sistema (os componentes de software e suas comunicações), e arquitetura de tecnologia (Spring Boot, PostgreSQL, LLM API, React Native, infraestrutura de cloud).
Os critérios de qualidade incluem performance (tempo de resposta da API abaixo de 3 segundos para consultas em cache, abaixo de 15 segundos para consultas que chamam o LLM), segurança (autenticação obrigatória, dados criptografados em trânsito e em repouso), usabilidade (o analista consegue realizar uma consulta completa em menos de 1 minuto sem treinamento prévio) e confiabilidade (taxa de uptime acima de 99% medida mensalmente).
Cybersecurity
A disciplina de Cybersecurity tem pontos de avaliação específicos e bem detalhados no material, e o SpecRadar os endereça todos de forma natural.
Na segurança de entrada e validação de dados, todos os campos da API — marca, modelo, versão e lista de atributos — passam por validação de tipo, tamanho máximo e caracteres permitidos antes de qualquer processamento. Isso previne SQL injection no banco, command injection no sistema e prompt injection no LLM. As mensagens de erro retornadas ao cliente nunca revelam stack trace, estrutura interna ou tecnologia utilizada — apenas um código de erro padronizado e uma mensagem amigável.
Na autenticação e autorização, o sistema implementa JWT com expiração configurável, assinatura forte e refresh token controlado. O controle de acesso baseado em papéis (RBAC) diferencia três níveis: analista comum (pode consultar e monitorar veículos), analista senior (pode definir o schema de atributos padrão da organização) e administrador (pode gerenciar usuários e acessar logs de auditoria).
Na proteção de APIs e serviços, toda comunicação usa HTTPS com TLS 1.2 mínimo. O rate limiting é implementado em dois níveis: por usuário (máximo de 20 consultas por hora para evitar abuso) e por IP (para evitar tentativas de enumeração). O CORS é configurado para permitir apenas os domínios autorizados da Ford. Um ponto específico desta proposta que outras não têm: o endpoint que chama o LLM tem rate limiting separado e mais restrito, porque cada chamada tem custo financeiro além do custo de segurança.
Na segurança de dados e privacidade, os dados armazenados no banco são dados técnicos de veículos (não dados pessoais de clientes), o que simplifica a questão de LGPD nesta proposta. No entanto, os dados de uso — quem consultou o quê e quando — são considerados dados corporativos sensíveis e são criptografados em repouso. Os logs de auditoria registram todas as consultas com usuário, timestamp e veículo consultado, mas nunca o conteúdo completo das mensagens de chat.
No monitoramento e auditoria, logs estruturados em formato JSON são gerados para cada requisição, incluindo tempo de resposta, status e identificação do usuário, sem dados sensíveis. Tentativas de autenticação falhadas consecutivas disparam alerta automático. Consultas em volume anormal (um usuário consultando centenas de veículos em minutos) são sinalizadas para revisão.
Inteligência Artificial e Machine Learning
A entrega desta disciplina segue exatamente o enunciado do professor — segmentação comportamental de clientes com dados sintéticos (Base 1) e modelagem preditiva com dados disponíveis no momento da compra (Base 2) — e é apresentada como o módulo analítico complementar da plataforma SpecRadar, reforçando a narrativa de que a Ford precisa entender não só os concorrentes, mas também o comportamento dos seus próprios clientes.
A etapa de segmentação usa a Base 1 com técnicas de clustering não supervisionado (K-Means ou DBSCAN, com justificativa da escolha baseada na natureza dos dados). A análise exploratória inicial identifica distribuições, valores faltantes e outliers. A escolha das variáveis de clustering é justificada com base na relevância para o comportamento de manutenção — frequência de retorno, intervalo entre revisões, tipo de serviço realizado, valor gasto. O número de clusters é determinado com método Elbow e Silhouette Score. Os clusters resultantes são interpretados e traduzidos em perfis de negócio com nomes descritivos — cliente fiel, cliente de abandono, cliente esquecido, cliente econômico — com análise das características predominantes de cada perfil.
A etapa de classificação usa a Base 2 estritamente com variáveis disponíveis no momento da compra, sem nenhuma variável de comportamento futuro, respeitando a regra crítica do enunciado. O modelo supervisionado (Random Forest ou XGBoost, com justificativa) é treinado com os clusters como variável-alvo. A avaliação usa accuracy, precision, recall, F1-score por classe e matriz de confusão. A leitura executiva dos resultados indica quais perfis são mais fáceis de prever (e portanto onde a intervenção proativa é mais viável), quais variáveis de compra são mais preditivas do comportamento futuro, e como a concessionária poderia usar esse modelo no dia a dia.
Validação da Solução
A validação pedida pela Ford — reproduzir todas as especificações da Ranger Raptor apresentadas no slide — é executada como demonstração ao vivo na apresentação. O grupo mostra o analista abrindo o app, digitando "Me dê as especificações completas da Ford Ranger Raptor" no chat, e o sistema retornando em segundos uma ficha com todos os campos: motor V6 3.0L Nano bi turbo, 397cv a 5650 RPM, torque máximo 583 Nm a 3500 RPM, transmissão AT de 10 velocidades com paddle shifters, tração 4WD, amortecedores Live Valve FOX Racing 2.5", tempo 0-100km/h de 5,8s, todos os sete modos de condução, modos de volante, escapamento e amortecedor, faróis Matrix LED, rodas e pneus 17" com 285/70 R17 AT, e preço R$499.000 — com o campo de preço marcado como "valor sujeito a alteração, verificar data da consulta" para demonstrar o tratamento correto de dados temporais.
Ponto Forte
O ponto forte central é que a solução resolve o problema da Ford de ponta a ponta com uma narrativa clara e uma demo concreta. O chatbot impressiona pela modernidade da interface, a API impressiona pela robustez arquitetural, o histórico temporal impressiona pela visão de produto de longo prazo, e a validação com a Ranger Raptor ao vivo fecha a apresentação de forma memorável. Nenhuma das partes existe de forma isolada — todas se reforçam mutuamente.
Ponto de Atenção
O custo de chamadas ao LLM é real e precisa ser gerenciado desde o início. A estratégia de cache é obrigatória, não opcional — sem ela, um grupo de analistas usando a plataforma intensamente pode gerar custos de API significativos em pouco tempo. O grupo deve definir desde a Sprint 1 qual é a política de cache (por quanto tempo uma consulta é considerada válida antes de buscar novamente na fonte) e apresentar isso como uma decisão arquitetural consciente, não como um detalhe de implementação.

Sprint 1 — FundaçãoPlataforma base com API REST completa e documentada, autenticação JWT com RBAC, banco de dados modelado com Flyway, app mobile com interface conversacional e interface estruturada funcionais, serviço de extração via LLM com cache, e validação com a Ranger Raptor. Entrega de ML conforme enunciado do professor.
Sprint 3 — MaturidadeAdição do histórico temporal com visualização de evolução de preços e specs, sistema de monitoramento com notificações push quando uma spec muda, refinamento do modelo de extração com base nos casos que falharam na Sprint 1, comparativo lado a lado aprimorado no app, e métricas de uso da plataforma disponíveis no painel administrativo.
Sprint 4 — MultimodalidadeIntegração da capacidade multimodal da proposta 1D — o sistema passa a aceitar PDF de catálogo, imagem e print de ficha técnica como entrada. Um novo endpoint POST /ingest/file recebe o arquivo, passa por OCR se necessário, envia para o modelo multimodal e armazena o resultado no mesmo banco com o mesmo schema. Isso fecha o ciclo do problema original da Ford, cobrindo até as fontes que nenhuma automação tradicional consegue processar.
Melhoria Possível Futura — Proposta 1B (Pipeline de Monitoramento Automatizado)
Esta é uma evolução que não será trabalhada nem citada nas entregas, mas que representa a maturidade máxima da plataforma caso o projeto continuasse além do ano letivo.
A ideia central é transformar o sistema de reativo em completamente proativo. Ao invés de esperar o analista fazer uma consulta, um pipeline agendado — inspirado no Apache Airflow que é parte do stack real da Ford — monitoraria periodicamente um conjunto pré-definido de veículos concorrentes e atualizaria o banco automaticamente quando detectasse mudanças.
O pipeline funcionaria em três etapas encadeadas. A primeira etapa de coleta tentaria buscar as especificações atualizadas de cada veículo monitorado a partir de fontes confiáveis — sites oficiais das montadoras, portais como Quatro Rodas e Webmotors, e APIs públicas de precificação como a Tabela FIPE. A segunda etapa de normalização passaria os dados coletados pelo mesmo serviço de extração via LLM já existente na plataforma, garantindo que o output sempre respeite o schema padronizado. A terceira etapa de comparação confrontaria o resultado atual com o registro mais recente no banco e, se houvesse diferença em qualquer campo, registraria a alteração no histórico e dispararia notificações para os analistas que monitoram aquele veículo.
O motivo pelo qual essa proposta foi deixada de fora do escopo principal é técnico e prático. Web scraping em sites de montadoras como Toyota, Volkswagen e Chevrolet enfrenta barreiras sérias — proteções anti-bot, JavaScript renderizado no cliente, bloqueio por IP após múltiplas requisições e mudanças frequentes de estrutura HTML que quebram seletores. Um pipeline que funciona perfeitamente na Sprint 1 pode estar completamente quebrado na Sprint 4 sem que o grupo perceba, e uma demo ao vivo com o pipeline falhando é pior do que não ter o pipeline. A abordagem de consulta sob demanda com cache resolve 80% do problema com 20% do risco técnico, o que é a escolha certa para um projeto acadêmico com prazo definido.
